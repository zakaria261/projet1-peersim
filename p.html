Comprendre notre projet DHT

Ce document explique le projet pas à pas, avec des mots simples. Pas besoin d'être expert — on va tout expliquer depuis le début.

Point de départ

C'est quoi une DHT ?

DHT veut dire Table de Hachage Distribuée (Distributed Hash Table). C'est un système qui permet de stocker et retrouver des données dans un réseau, sans serveur central.

🌞 Analogie du quotidien
Imagine une bibliothèque géante où il n'y a pas de bibliothécaire central. Chaque livre est rangé chez une personne différente. Quand tu veux un livre, tu demandes à un voisin, qui demande à son voisin, jusqu'à trouver qui l'a. C'est exactement ce que fait une DHT : chaque nœud (= chaque "ordinateur") stocke une partie des données.

Dans notre projet, on a construit cette DHT en Java, en simulant plusieurs ordinateurs qui communiquent entre eux, tous sur la même machine grâce au simulateur PeerSim.

Le problème que ça résout

Si tu as des données à stocker sur Internet (comme BitTorrent, ou Spotify dans les débuts), tu ne veux pas dépendre d'un seul serveur. Si ce serveur tombe en panne, tout s'arrête. Avec une DHT :

  • Les données sont réparties sur plein de machines
  • Si une machine tombe, les données existent encore ailleurs
  • Aucun nœud n'a le contrôle total — c'est décentralisé
L'outil

PeerSim : notre simulateur

PeerSim est un simulateur de réseau P2P écrit en Java. Plutôt que de déployer notre DHT sur de vraies machines sur Internet, on simule un réseau entier sur un seul ordinateur.

🌞 Analogie
C'est comme jouer à un jeu de simulation de ville : tu ne construis pas de vraies maisons, mais tu peux tester comment la ville fonctionne. PeerSim fait pareil avec un réseau d'ordinateurs.

Comment on l'utilise

On a choisi le mode Event-Driven de PeerSim. Ça veut dire que tout se passe par événements (comme la vraie vie) : un nœud envoie un message → l'autre le reçoit un peu plus tard → il répond, etc. C'est plus réaliste que le mode "tout le monde fait la même chose en même temps".

Fichier de config : conf/config.cfg
C'est le fichier qui dit à PeerSim combien de nœuds créer (10 ici), combien de temps faire tourner la simulation (1000 unités de temps), et quels protocoles utiliser.

Lancer le projet

Sous Eclipse :

  1. Importer le dossier comme projet Java
  2. Ajouter les .jar du dossier lib/ au Build Path
  3. Lancer la classe peersim.Simulator avec l'argument conf/config.cfg
La structure de base

L'anneau : comment les nœuds sont organisés

Dans notre DHT, tous les nœuds sont organisés en forme d'anneau. Chaque nœud a un identifiant unique (un grand nombre aléatoire), et les nœuds sont triés par identifiant dans l'anneau.

🌞 Analogie
Imagine des personnes assises autour d'une table ronde. Chaque personne a un numéro, et elles sont assises dans l'ordre de leurs numéros. Chaque personne connaît uniquement ses deux voisins directs : celui de gauche et celui de droite. C'est tout. Elle ne connaît personne d'autre autour de la table.

Voici à quoi ressemble notre anneau avec 10 nœuds :

N0
ID: 120
→
N1
ID: 230
→
N2
ID: 450
→
N3
ID: 670
→
… →
→
N9
ID: 990
→ (retour à N0)

Chaque nœud connaît son prédécesseur (pred = le nœud juste avant lui) et son successeur (succ = le nœud juste après lui). C'est tout ce qu'il sait.

Les identifiants et la responsabilité

Chaque donnée qu'on stocke a aussi un identifiant (une clé). La règle est simple : c'est le nœud dont l'ID est le plus proche supérieur à la clé qui est responsable de cette donnée.

🌞 Exemple concret
Les nœuds ont les IDs : 120, 230, 450, 670...
On veut stocker une donnée avec la clé 380.
→ Le nœud responsable est celui avec l'ID 450 (le premier nœud dont l'ID est ≥ 380).
Étape 1 — Partie A

Rejoindre l'anneau (JOIN)

Au départ, il n'y a qu'un seul nœud dans l'anneau (N0). Il est son propre voisin de gauche ET de droite. Ensuite, les autres nœuds arrivent un par un et doivent trouver leur place.

Comment un nouveau nœud rejoint l'anneau ?

1
Le nouveau nœud envoie une demande à N0 Il envoie un message JOIN_REQUEST à N0 (le seul nœud qu'il connaît, le "point de contact"). Ce message contient son propre ID.
2
N0 cherche la bonne place et fait circuler le message N0 regarde : "est-ce que le nouveau doit être entre moi et mon successeur ?" Si non, il passe le message à son successeur, qui fait la même question, et ainsi de suite.
3
Un nœud trouve la bonne place Un nœud X se rend compte que le nouveau nœud doit être placé entre lui et son successeur. Il met à jour ses pointeurs et notifie tout le monde.
4
L'anneau est mis à jour Le nouveau nœud reçoit ses voisins (pred et succ). L'ancien successeur de X est notifié que son nouveau prédécesseur est le nouveau nœud.
🌞 Analogie
C'est comme rejoindre une file d'attente déjà formée en cercle. Tu demandes au premier de la file où est ta place selon ton numéro. Il te dit "passe à mon voisin", ton voisin dit "passe au suivant"... jusqu'à ce que quelqu'un dise "ta place c'est entre moi et mon voisin !". Il s'écarte, tu t'insères, et tu te présentes à tes nouveaux voisins.

La condition d'insertion dans le code

Comment un nœud sait-il que le nouveau doit s'insérer entre lui et son successeur ? Il vérifie que le nouvel ID est compris entre son propre ID et celui de son successeur.

La condition d'insertion — DHTNode.java 
// Cas normal : mes IDs sont, par exemple, moi=230 et monSuccesseur=450
// Le nouveau doit être entre 230 et 450
if (monId < idSuccesseur) {
    inBetween = (nouvelId > monId) && (nouvelId < idSuccesseur);
}

// Cas particulier (wraparound) : moi=900, successeur=120
// L'anneau "boucle", donc le nouveau est ici si son ID > 900 OU < 120
else if (monId > idSuccesseur) {
    inBetween = (nouvelId > monId) || (nouvelId < idSuccesseur);
}

if (inBetween) {
    // J'ai trouvé sa place ! Je réorganise les liens
    monSuccesseur = nouveauNoeud;
    envoyer(JOIN_ACCEPTED, nouveauNoeud);   // Je lui donne ses voisins
    envoyer(UPDATE_PRED, ancienSuccesseur); // Je préviens l'ancien voisin
} else {
    // Pas ici, je fais suivre au nœud d'après
    transmettre(message, monSuccesseur);
}
Le cas "wraparound" : l'anneau est circulaire. Les IDs vont de 0 à un très grand nombre, et après le plus grand ID on revient au plus petit. Du coup, le nœud avec l'ID le plus grand a pour successeur le nœud avec l'ID le plus petit. Il faut gérer ce cas spécialement.
Étape 1 — Partie B

Quitter l'anneau (LEAVE)

Quand un nœud veut quitter le réseau proprement, il doit prévenir ses voisins pour que l'anneau ne se casse pas.

Ce qui se passe

Avant de partir, le nœud N2 (par exemple) dit à ses voisins de se connecter directement :

Avant :
N1
→
N2
→
N3
Après :
N1
→ (lien direct) →
N3
1
N2 envoie un message à son prédécesseur N1 Il lui dit : "Mon successeur était N3, maintenant c'est ton nouveau successeur."
2
N2 envoie un message à son successeur N3 Il lui dit : "Mon prédécesseur était N1, maintenant c'est ton nouveau prédécesseur."
3
N2 efface ses propres liens et disparaît L'anneau est maintenant reformé sans N2. N1 et N3 se connaissent directement.
Départ propre — leaveNetwork() dans DHTNode.java 
public void leaveNetwork() {
    // Je préviens mon prédécesseur : "prends N3 comme successeur"
    envoyer(UPDATE_SUCC, monSuccesseur, monPred);

    // Je préviens mon successeur : "prends N1 comme prédécesseur"
    envoyer(UPDATE_PRED, monPred, monSuccesseur);

    // J'efface mes propres liens, je suis parti
    monPred    = null;
    monSuccesseur = null;
}
Comment on vérifie que ça marche ?
La classe RingObserver parcourt l'anneau toutes les 200 unités de temps. Elle suit les liens succ de nœud en nœud et compte combien elle en trouve. Si le compte est bon et qu'il n'y a pas de lien cassé (succ == null), l'anneau est intact.
Étape 2

Envoyer un message à travers le réseau (SEND / DELIVER)

Maintenant qu'on a notre anneau, on veut qu'un nœud puisse envoyer un message à un autre nœud, même s'il ne le connaît pas directement.

🌞 Analogie
C'est comme le jeu du "téléphone arabe" mais utile : tu passes ton message à ton voisin, qui le passe à son voisin, jusqu'à ce qu'il arrive à destination. Chaque nœud regarde si c'est pour lui, sinon il le fait suivre.

Comment un nœud sait-il si le message est pour lui ?

Chaque message a une clé cible (targetId). Un nœud est responsable de cette clé si elle est comprise entre son prédécesseur et lui-même.

🌞 Exemple
Nœuds dans l'anneau : 120, 230, 450, 670...
Message pour la clé 350.
→ Le nœud 230 reçoit le message. Il vérifie : est-ce que 350 est entre 230 et 450 ? Oui, mais 350 > 230 et ≤ 450, donc c'est le nœud 450 qui est responsable, pas lui.
→ Il transmet à 450, qui dit "c'est pour moi !" et délivre le message.
Logique de routage — handleRouting() dans DHTNode.java 
// Est-ce que la clé cible est dans mon intervalle de responsabilité ?
// Mon intervalle : ]monPred.id, monId]
boolean cEstPourMoi = (cle > pred.id) && (cle <= monId);

if (cEstPourMoi) {
    // Le message est arrivé à destination !
    System.out.println(">>> DELIVER: reçu !");
} else {
    // Pas pour moi, je transmets au nœud suivant
    System.out.println("[FORWARD] je transmets au nœud suivant");
    envoyer(message, monSuccesseur);
}

Ce qu'on voit dans la console

Quand on lance le projet, on voit exactement comment les messages voyagent :

Exemple de sortie console 
  [FORWARD] Node 230 passe le relai au Node 450
  [FORWARD] Node 450 passe le relai au Node 670

Étape 3

Stocker et récupérer des données (PUT / GET)

Maintenant on va vraiment stocker des données dans la DHT. Chaque nœud a son propre "tiroir" pour ranger des données dont il est responsable.

Stocker une donnée (PUT)

1
Un nœud veut stocker la donnée "Mon super projet M1" avec la clé 380 Il envoie un message PUT_DATA avec la clé et la donnée dans le réseau.
2
Le message est routé jusqu'au nœud responsable de la clé 380 Comme vu dans l'étape 2, le message passe de nœud en nœud jusqu'au responsable (ici le nœud 450).
3
Le nœud 450 stocke la donnée dans son "tiroir principal" (dataStore) La donnée est maintenant enregistrée chez lui.
4
Il envoie aussi une copie à son prédécesseur ET à son successeur C'est la réplication : on garde 3 copies de chaque donnée (chez le responsable + ses 2 voisins directs).

Pourquoi 3 copies ?

Tolérance aux pannes : Si le nœud responsable tombe en panne, ses voisins ont encore la donnée. On ne perd rien. C'est le degré de réplication = 3.
Stockage avec réplication — DHTNode.java 
// Je suis le responsable de cette clé, je stocke la donnée
dataStore.put(cle, donnee);   // Mon tiroir principal

// J'envoie une copie à mon voisin de gauche (prédécesseur)
envoyer(STORE_REPLICA, donnee, monPred);

// J'envoie une copie à mon voisin de droite (successeur)
envoyer(STORE_REPLICA, donnee, monSuccesseur);

// Résultat : 3 copies existent dans le réseau → degré de réplication = 3

Récupérer une donnée (GET)

1
Un nœud envoie une demande GET avec la clé 380 Le message est routé jusqu'au nœud responsable (comme pour le PUT).
2
Le responsable cherche dans son dataStore S'il trouve → il répond avec la donnée. S'il ne trouve pas (il est peut-être arrivé récemment et a hérité les données d'un nœud parti) → il regarde dans son replicaStore (tiroir de copies).
3
Il renvoie la donnée au nœud qui avait demandé On voit dans la console : <<< RECEIVED REPLY: "Mon super projet M1"
Étape 4

Aller plus vite : les liens longs (piggybacking)

Le problème du routage de base

Avec notre routage de base, un message doit passer par chaque nœud un par un. Si on a 1000 nœuds, il faut en moyenne 500 sauts pour livrer un message. C'est très lent. On dit que la complexité est O(N) — ça grossit avec le nombre de nœuds.

🌞 Analogie
Si tu veux envoyer une lettre à quelqu'un de l'autre côté de la ville, au lieu de passer par tous les voisins un par un, tu pourrais la donner directement à quelqu'un qui habite plus près de la destination. C'est ça, les "liens longs" : des raccourcis vers des nœuds plus lointains.

Notre solution : le piggybacking

L'idée est très simple : à chaque fois qu'on reçoit un message, on regarde d'où il vient. L'expéditeur devient un "contact" qu'on ajoute dans notre liste de raccourcis (longLinks). Au fur et à mesure, on accumule jusqu'à 5 raccourcis vers des nœuds éloignés, sans jamais demander à un serveur central.

🌞 Analogie
C'est comme quand tu rencontres des gens au hasard dans la vie. Chaque fois que quelqu'un te parle, tu notes son nom et sa ville dans ton carnet. La prochaine fois que tu dois envoyer quelque chose dans cette direction, tu appelles directement cette personne plutôt que de passer par tous tes voisins.
Apprentissage passif — à chaque message reçu, DHTNode.java 
// Dès qu'on reçoit n'importe quel message...
// Si l'expéditeur est quelqu'un qu'on ne connaît pas encore
// et qu'on a de la place dans notre liste (max 5) :
if (message.expéditeur != null
  && !maListeDeRaccourcis.contains(message.expéditeur)
  && maListeDeRaccourcis.size() < 5) {

    maListeDeRaccourcis.add(message.expéditeur);
    // On a appris un nouveau raccourci !
}

Comment on utilise ces raccourcis pour router plus vite

Quand on doit faire suivre un message, au lieu d'envoyer juste au voisin direct, on compare toutes nos options et on choisit celle qui est la plus proche de la destination.

Choix du meilleur saut — handleRouting() dans DHTNode.java 
// Par défaut, on envoie au voisin direct (successeur)
meilleureOption = monSuccesseur;
meilleureDistance = distance(monId, cible);

// On regarde dans notre liste de raccourcis
for (Noeud raccourci : maListeDeRaccourcis) {
    distanceViaRaccourci = distance(raccourci.id, cible);

    if (distanceViaRaccourci < meilleureDistance) {
        meilleureDistance = distanceViaRaccourci;
        meilleureOption = raccourci; // Ce raccourci est mieux !
    }
}

// On envoie par le meilleur chemin trouvé
if (meilleureOption == monSuccesseur)
    log("[FORWARD] je passe au nœud suivant normal");
else
    log("[SHORTCUT] j'utilise un raccourci !");

envoyer(message, meilleureOption);

Résultat : beaucoup moins de sauts

Avec les raccourcis, un message qui aurait pris 500 sauts n'en prend plus que 10 à 15. On passe d'une complexité O(N) à O(log N).

🌞 Pourquoi on n'a pas "triché" ?
On aurait pu utiliser la vue globale de PeerSim pour assigner des raccourcis parfaits dès le départ. Mais ça ne serait pas réaliste : dans un vrai réseau distribué, aucun nœud ne connaît tous les autres. Notre approche piggybacking est réaliste : on apprend les raccourcis naturellement en recevant des messages, comme dans la vraie vie.

Comprendre la structure du code

Voici les 7 fichiers Java du projet et ce qu'ils font en termes simples :

Fichier Ce qu'il fait en simple
DHTNode.java Le cerveau de chaque nœud. Contient toute la logique : join, leave, routage, stockage, piggybacking. C'est le fichier principal.
Message.java La définition d'un message. Comme une enveloppe : elle a un type (JOIN, PUT, GET...), un contenu, un expéditeur, et une destination.
CustomInitializer.java Le "démarreur". Il crée le premier nœud, programme les joins des autres nœuds, et planifie les tests (Leave, Send, Put, Get) à des moments précis.
RingObserver.java Le "vérificateur". Il parcourt l'anneau régulièrement et affiche l'état de chaque nœud pour confirmer que tout va bien.
LeaveControl.java Déclenche le départ d'un nœud spécifique pour tester le Leave.
SendControl.java Envoie un message de test d'un nœud à un autre pour tester le routage.
StorageControl.java Teste le PUT puis le GET : stocke une donnée et vérifie qu'on peut la récupérer.

Les données dans DHTNode

Voici ce que chaque nœud "sait" et "possède" :

Les données de chaque nœud — DHTNode.java 
public class DHTNode {

    // Son identifiant unique (un grand nombre aléatoire)
    public long id;

    // Ses deux voisins dans l'anneau
    public Node pred;   // voisin de gauche
    public Node succ;   // voisin de droite

    // Ses tiroirs de données (étape 3)
    HashMap<Long, Object> dataStore;     // données dont il est responsable
    HashMap<Long, Object> replicaStore;  // copies de sauvegarde de ses voisins

    // Ses raccourcis (étape 4)
    ArrayList<Node> longLinks;  // max 5 raccourcis appris par piggybacking
}
