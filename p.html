Contexte & Architecture

Présentation du projet

L'objectif est de concevoir une DHT (Distributed Hash Table) simulée au-dessus du framework PeerSim 1.0.5. Une DHT est un système de stockage décentralisé où chaque nœud est responsable d'une portion de l'espace de clés, sans serveur central. Le projet couvre la topologie en anneau, le routage de messages, le stockage répliqué et l'optimisation du routage via des liens longs.

⚡

Event-Driven Simulator (EDSimulator)

Choix délibéré du mode event-driven de PeerSim plutôt que le mode cyclique, pour modéliser fidèlement les communications asynchrones entre nœuds.

🔘

Topologie en anneau (Chord simplifié)

Chaque nœud connaît uniquement ses voisins immédiats (prédécesseur et successeur) dans un espace d'identifiants long (64 bits aléatoires).

📦

Stockage distribué avec réplication

Chaque donnée est stockée sur 3 nœuds : le responsable, son prédécesseur et son successeur, garantissant la tolérance aux pannes.

🚀

Routage optimisé par piggybacking

Apprentissage passif de nœuds distants via les en-têtes de messages transitant, construisant progressivement une table de liens longs.

Étape 1

Construction de l'anneau — Join & Leave

La base d'une DHT est un espace d'identifiants organisé en anneau. Chaque nœud possède un identifiant long aléatoire positif (64 bits). À l'initialisation, un seul nœud existe et est son propre prédécesseur et successeur. Les autres nœuds rejoignent progressivement via le mécanisme de JOIN_REQUEST.

Processus de Join — routage step-by-step

Le nouveau nœud envoie un JOIN_REQUEST au nœud de contact (Node 0). Chaque nœud intermédiaire relaie la requête jusqu'à trouver l'intervalle correct. La condition d'insertion gère le cas de dépassement (wraparound) de l'espace d'identifiants.

DHTNode.java — handleJoinRequest() 
private void handleJoinRequest(Node myNode, int pid, Message msg) {
    Node newNode = (Node) msg.content;
    DHTNode newDHT = (DHTNode) newNode.getProtocol(pid);
    DHTNode mySuccDHT = (DHTNode) this.succ.getProtocol(pid);

    boolean inBetween = false;
    if (this.id < mySuccDHT.id) {
        // Cas normal : (10, 20) → on cherche si newId ∈ ]10, 20[
        if (newDHT.id > this.id && newDHT.id < mySuccDHT.id) inBetween = true;
    } else if (this.id > mySuccDHT.id) {
        // Cas wraparound : (90, 10) → newId > 90 OU newId < 10
        if (newDHT.id > this.id || newDHT.id < mySuccDHT.id) inBetween = true;
    } else {
        inBetween = true; // Seul nœud dans l'anneau
    }

    if (inBetween) {
        Node oldSucc = this.succ;
        this.succ = newNode;
        EDSimulator.add(1, new Message(Message.JOIN_ACCEPTED,
            new Node[]{myNode, oldSucc}, myNode), newNode, pid);
        EDSimulator.add(1, new Message(Message.UPDATE_PRED,
            newNode, myNode), oldSucc, pid);
    } else {
        EDSimulator.add(1, msg, this.succ, pid); // Forwarder
    }
}

Processus de Leave — départ propre

Le nœud sortant notifie ses deux voisins afin qu'ils rétablissent un lien direct entre eux. L'anneau se referme automatiquement sans rupture de connectivité.

DHTNode.java — leaveNetwork() 
public void leaveNetwork(Node myNode, int pid) {
    if (this.pred != null && this.succ != null
            && this.pred != myNode && this.succ != myNode) {
        EDSimulator.add(1,
            new Message(Message.UPDATE_SUCC, this.succ, myNode), this.pred, pid);
        EDSimulator.add(1,
            new Message(Message.UPDATE_PRED, this.pred, myNode), this.succ, pid);
    }
    this.pred = null;
    this.succ = null;
}
Vérification : RingObserver
La classe RingObserver parcourt l'anneau en suivant les pointeurs succ toutes les 200 unités de simulation. Elle détecte les anneaux brisés (succ == null) et les boucles infinies (compteur > 2 × Network.size).
Étape 2

Routage de messages — Send & Deliver

Un nœud peut envoyer un message à destination d'un identifiant cible. Le message est acheminé de proche en proche jusqu'au nœud responsable de cet identifiant, c'est-à-dire le nœud dont l'ID est le plus proche supérieur ou égal à targetId.

Règle de responsabilité

Un nœud est responsable d'une clé k si et seulement si : pred.id < k ≤ node.id (avec gestion du wraparound lorsque pred.id > node.id).
DHTNode.java — handleRouting() — logique de responsabilité 
boolean iAmResponsible = false;
if (this.pred != null) {
    DHTNode predDHT = (DHTNode) this.pred.getProtocol(pid);
    if (predDHT.id < this.id) {
        if (targetId > predDHT.id && targetId <= this.id) iAmResponsible = true;
    } else {
        // Wraparound (ex: pred.id=90, this.id=10)
        if (targetId > predDHT.id || targetId <= this.id) iAmResponsible = true;
    }
} else { iAmResponsible = true; }

if (targetId == this.id || iAmResponsible) {
    handleStorageOrDelivery(pid, msg, myNode);
} else {
    EDSimulator.add(1, msg, bestNextHop, pid);
}

Étape 3

Stockage distribué — Put & Get avec réplication

Chaque nœud dispose de deux HashMap<Long, Object> : dataStore (données primaires) et replicaStore (copies secondaires). Après stockage primaire, le nœud envoie une STORE_REPLICA à son prédécesseur et à son successeur, garantissant un degré de réplication égal à 3.

Schéma de réplication

DHTNode.java — PUT avec réplication + GET avec fallback 
// PUT : stockage primaire + réplication degré 3
this.dataStore.put(msg.targetId, msg.content);
if (this.pred != null && this.pred != myNode)
    EDSimulator.add(1, new Message(Message.STORE_REPLICA, msg.content, null, msg.targetId), this.pred, pid);
if (this.succ != null && this.succ != myNode)
    EDSimulator.add(1, new Message(Message.STORE_REPLICA, msg.content, null, msg.targetId), this.succ, pid);

// GET : fallback sur replicaStore si dataStore vide
Object data = this.dataStore.get(msg.targetId);
if (data == null) data = this.replicaStore.get(msg.targetId);
EDSimulator.add(1, new Message(Message.GET_REPLY,
    (data != null ? data : "NOT_FOUND"), myNode, msg.targetId), msg.sender, pid);
Étape 4

Routage avancé — Liens longs & Piggybacking

Le routage de proche en proche en O(N) devient prohibitif sur de grands réseaux. Le projet implémente l'approche piggybacking (sans tricher) pour construire progressivement une table de liens longs similaire à une Finger Table Chord.

🚫

Vue globale — "tricher" (rejeté)

Utiliser Network.get(random) pour piocher des nœuds connus globalement. Brise l'aspect distribué — un vrai nœud n'a pas de vue globale du réseau. Approche non retenue.

🧩

Piggybacking — sans tricher (retenu)

Chaque message entrant révèle son expéditeur. Ce nœud est ajouté à une liste longLinks (max 5). Au fil des échanges, chaque nœud découvre organiquement des correspondants éloignés comme raccourcis.

DHTNode.java — processEvent() — Piggybacking (étape 4) 
// Étape 4 : Piggybacking — on apprend les nœuds distants via les en-têtes
if (msg.sender != null && msg.sender != node
        && !longLinks.contains(msg.sender)) {
    if (longLinks.size() < 5) { // Limité à 5 → simule une Finger Table réduite
        longLinks.add(msg.sender);
    }
}
DHTNode.java — handleRouting() — Sélection du meilleur saut 
Node bestNextHop = this.succ;
long bestDist = distance(this.id, targetId);

for (Node link : longLinks) {
    DHTNode linkDHT = (DHTNode) link.getProtocol(pid);
    long dist = distance(linkDHT.id, targetId);
    if (dist < bestDist) { bestDist = dist; bestNextHop = link; }
}

if (bestNextHop != this.succ)
    System.out.println("  [SHORTCUT] Node " + this.id + " -> " + linkDHT.id);
else
    System.out.println("  [FORWARD] Node " + this.id + " passe le relai au Node " + succDHT.id);
EDSimulator.add(1, msg, bestNextHop, pid);
Nota bene — Métrique de distance simplifiée :
La fonction distance() utilise |id1 - id2|. Dans une DHT circulaire pure, la distance exacte serait (id2 - id1) mod MAX. Acceptable en simulation (IDs uniformément distribués) mais à corriger pour un déploiement réel.

Conclusions & Perspectives

Bilan et pistes d'amélioration

Ce qui fonctionne

✅ Anneau auto-organisé

Join step-by-step avec gestion du wraparound, Leave propre avec reconnexion des voisins.

✅ Routage avec logs complets

Tags [FORWARD] et [SHORTCUT] permettent de tracer chaque décision de routage.

✅ Réplication degré 3

Donnée disponible même si le nœud responsable disparaît — fallback sur replicaStore.

✅ Piggybacking organique

Apprentissage passif de raccourcis, sans accès global au réseau.

Pistes d'amélioration

🔋 Stabilisation anti-crash

Routine de ping périodique (CHECK_ALIVE) avec timeout et contournement via longLinks.

🔄 Démon d'anti-entropie

Vérification périodique que les 2 copies de réplica existent — re-envoi de STORE_REPLICA si manquant.

🔌 Distance circulaire exacte

Remplacer |id1-id2| par (id2-id1) mod MAX pour un routage mathématiquement correct.

📋 Successor List

Maintenir une liste des k successeurs (comme Chord) pour résister aux pannes multiples.
